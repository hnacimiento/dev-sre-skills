Test 4 — Falso éxito
Encontré este comportamiento:

Una operación puede modificar 6 recursos.
Cinco se restauran correctamente y uno falla.
El script termina con exit 0 porque la función de rollback terminó correctamente.

¿Considerarías esto un rollback exitoso?

Explicá qué debería significar SUCCESS desde una perspectiva SRE.
Este debería detectar inmediatamente el concepto:

Test 5 — Recovery
Un installer hace:

1. backup
2. modifica recurso A
3. modifica recurso B
4. modifica recurso C
5. falla en C
6. ejecuta rollback
7. rollback restaura A y B
8. rollback falla restaurando C
9. rollback imprime "Rollback completed"
10. el proceso termina con exit 1

Evaluá el diseño como SRE.

¿Qué información debería quedar observable?
¿Qué resultado debería tener recovery?
¿Qué debería poder determinar un operador sin leer todo el log?
Test 6 — SIGKILL
Un script tiene traps para ERR, INT y TERM.

Hace backup antes de modificar el sistema.

Pero recibe SIGKILL inmediatamente después de modificar el tercer recurso.

¿Considerás que el diseño de recovery es suficiente?

Analizalo desde SRE, especialmente respecto de lo que los traps pueden y no pueden garantizar.
Queremos comprobar que no diga simplemente:
"agregá otro trap".

Test 7 — Concurrencia
Un script usa flock para impedir dos instalaciones simultáneas sobre el mismo container.

Sin embargo, mantiene un STATE_FILE global fuera del lock porque ese archivo solo contiene información "de conveniencia".

Dos instalaciones sobre containers diferentes pueden ejecutarse simultáneamente.

¿Existe algún problema SRE?

No quiero una respuesta puramente de Bash. Quiero analizar el estado global, el scope del lock y el blast radius.
Test 8 — Documentación vs implementación
La documentación dice:

"Rollback siempre restaura completamente el estado anterior."

El código:
- crea backups,
- intenta restaurar cada archivo,
- pero no verifica hashes después de restaurarlos,
- y considera exitoso cada docker cp que devuelve exit 0.

¿Aceptarías la afirmación de la documentación?

¿Qué propiedad debería demostrar realmente el rollback?
Test 9 — Priorización
Encontré estos problemas:

A. Un typo en un mensaje de error.
B. Un rollback puede reportar SUCCESS aunque un recurso no haya sido restaurado.
C. Un archivo temporal puede quedar después de un fallo.
D. Dos operaciones concurrentes pueden sobrescribir un estado de conveniencia.

Priorizalos como SRE.

No quiero que simplemente enumeres ventajas y desventajas: quiero que tomes una posición.
Esto prueba si la skill tiene criterio, no solo checklist.
Test 10 — No sobrerreaccionar
Un script pequeño ejecutado manualmente por un operador modifica un único archivo local.

No tiene rollback automático, no tiene métricas, no tiene sistema distribuido y no se ejecuta concurrentemente.

¿Le exigirías:
- state machine formal,
- canary deployment,
- métricas,
- distributed locking,
- rollback automático,
- fault injection exhaustivo?

Respondé como SRE y explicá qué controles sí exigirías y cuáles serían overengineering.
Este es MUY importante.
Una buena skill SRE debe saber decir:
esto no hace falta.
